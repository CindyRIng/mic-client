# ADR-0006：文档先行（docs-first）工作流

- 状态：Accepted
- 日期：2026-11-15
- 关联：[docs/README.md](../README.md)、[08 路线图](../08-roadmap.md)

## 背景

- 项目目标依赖**未公开接口**（随时可能改版）、多层风控与验证码、以及若干事实性口径（会员等级、匿名字段边界、地区词行为），若先写代码再补文档，容易出现：字段/错误码/枚举多套命名、实现与事实不符、返工。
- 用户明确要求「先不要进入开发，先做一套非常完整详细的文档，从需求到接口设计等等」。

## 决策

1. **M0 阶段只产出文档**：`docs/01–08` + `research/` + `decisions/`；
2. 实现阶段遵循：**需求 → 设计 → 接口 → 测试** 的文档基线，任何行为变更先改文档（或补 ADR）；
3. 文档有固定契约（FR/NFR/AC 编号、错误码、枚举、响应包），所有文档与实现共用；
4. 文档状态机：Draft → Review → Approved，Lead 评审通过后进入实现；
5. 评审检查清单见 [docs/README.md](../README.md) §4。

## 后果

**正面**：契约稳定、返工少、可评审、可交给其他 Agent 按文档实现；事实有证据链。
**负面**：前期投入大、文档需要维护。
**缓解**：文档模板化、编号/错误码统一、变更走 ADR、Lead 定期对齐。

## 替代方案

- **边写代码边补文档**：短期快，长期口径漂移 → 不采用。
- **只写一份大文档**：难维护/难评审 → 不采用（编号拆分 + research 证据分离）。

## 证据

- 本次交付：`docs/01–08`、`docs/decisions/`、`docs/research/`、根 `README.md`
- 用户要求原文：先整理目录 + 完整文档，不进入开发
